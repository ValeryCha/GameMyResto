# Система гостей: вместимость, спрос, оборот и очередь

Документ является проектной спецификацией. Реализация выполняется отдельными задачами.

## 1. Разделение метрик

Вместо одного `targetGuestCount` используются три независимые величины в единицах «гости» или «гости/тик»:

- `capacity` — сколько гостей можно посадить одновременно.
- `arrivalRate` — сколько новых гостей хотят прийти за тик.
- `throughput` — сколько гостей ресторан способен обслуживать за тик при текущей команде и оборудовании.

Для интерфейса значения потока удобнее показывать за 60 тиков: `rate60 = 60 × rate`.

### 1.1. Вместимость

```text
capacity = usableSeats
```

`usableSeats` — стулья, примыкающие к обычному или двойному столу. Уровень, слоты и число официантов не добавляют сидячих мест.

Если `capacity = 0`, новые гости могут образовать только ограниченную очередь; посадка невозможна.

### 1.2. Спрос

Базовое предложение:

```text
levelDemand = 0.12 + 0.012 × (level - 1)
slotDemand  = 0.03 × purchasedGuestSlots
ratingFactor = 0.75 + 0.50 × popularity / 100
peakFactor = 1.50 во время пика, иначе 1.00

arrivalRate = (levelDemand + slotDemand) × ratingFactor × peakFactor
spawnProgress += arrivalRate каждый тик
```

Когда `spawnProgress >= 1`, создаётся одна попытка прихода и из прогресса вычитается 1. Дробный остаток сохраняется. Это устраняет необходимость искусственного минимального интервала и позволяет плавно представлять низкий спрос.

Диапазон при рейтинге 50 вне пика:

- Уровень 1 без слотов: 0.12 гостя/тик, 7.2 за 60 тиков.
- Уровень 33 без слотов: 0.504 гостя/тик, 30.24 за 60 тиков.
- Каждый слот на любом уровне: +0.03 до рейтингового множителя; при рейтинге 50 — ровно +1.8 гостя за 60 тиков.

Слот увеличивает **спрос**, а не сидячие места. Поэтому покупка остаётся полезной на 33 уровне, но требует подготовленного ресторана.

### 1.3. Пропускная способность

Обозначения:

```text
C = clamp(0, 5, chefs)        // повара, валидная рабочая конфигурация 1..5
S = clamp(0, 5, stoves)       // плиты, валидная рабочая конфигурация 1..5
W = clamp(0, 5, waiters)      // официанты, валидная рабочая конфигурация 1..5
K = clamp(0, 5, counters)     // стойки, валидная рабочая конфигурация 1..5
U = cooking upgrade, 0..5
V = waiter upgrade, 0..5
B = суммарный бонус скинов кухни, 0..0.05
D = 0.92                      // детерминированные маршруты официантов
T_cook = 8                    // базовые тики блюда; калибруется по каталогу
T_service = 10                // базовый цикл выдачи и доставки
T_eat = 8                     // текущее время еды
```

Формулы:

```text
cookTimeFactor = (1 - 0.08 × U) × (1 - B)
kitchenRate = min(C, S) / (T_cook × cookTimeFactor)

waiterSpeed = 1 / (1 - 0.07 × V)
serviceRate = D × min(W, K) × waiterSpeed / T_service

seatRate = capacity / (T_service / max(1, min(W, K)) + T_eat)
throughput = min(kitchenRate, serviceRate, seatRate)
```

Свойства:

- Число рабочих кухонных пар равно `min(C, S)`, а не всегда 1.
- Число активных линий выдачи равно `min(W, K)`.
- Отсутствие поваров, плит, официантов или стоек делает соответствующее звено нулевым. До LOGIC-7 дефолтная кухня считается 1/1.
- Прокачка кухни и скины умножают время, поэтому кап `B = 0.05` невозможно обойти количеством скинов.
- `D = 0.92` резервирует 8% на неоптимальное распределение `waiterIndex % counters.length`; это осознанный трейд-офф, а не требование менять маршрутизацию.
- `seatRate` не позволяет высокой кухне обслуживать больше гостей, чем позволяет оборот сидячих мест.

Это расчётный ориентир, а не телепортация гостей: фактическая симуляция по-прежнему использует маршруты, заказы и состояния сотрудников. После реализации коэффициенты `T_cook`, `T_service` и `D` калибруются длительными тестами.

### 1.4. Лимитирующее звено

Для HUD выбирается минимум из `kitchenRate`, `serviceRate`, `seatRate`. При равенстве приоритет: места → кухня → доставка. Показывается одна понятная подсказка: «Не хватает мест», «Кухня не успевает» или «Официанты не успевают».

`arrivalRate > throughput` не блокирует приход гостей: это нормальный источник очереди и риска.

## 2. Жизненный цикл гостя

```text
spawn → свободное место → посадка → заказ → еда → расчёт → уход
      → нет места и очередь не полна → queueWaiting
      → очередь полна → queueRejected → уход
```

1. При появлении гость сначала пытается занять пригодное место.
2. Если места нет, он добавляется в конец FIFO-очереди.
3. Освободившееся место предлагается первому гостю очереди.
4. Если первый гость не может дойти до места, маршрут пересчитывается; место ненадолго резервируется, чтобы следующий гость не занял его.
5. Гость из очереди проходит стандартные состояния заказа и обслуживания.

## 3. Очередь у входа

### 3.1. Лимит и терпение

- Максимум: **5 гостей**.
- Базовое терпение: **90 тиков**.
- Индивидуальный лимит: `queuePatience = 90 × patienceMultiplier(state)`.
- Таймер начинается при постановке и не уменьшается во время движения к уже зарезервированному месту.

### 3.2. Полная очередь

Новый гость при полной очереди сразу уходит:

```text
popularity -= 1
satisfiedStreak = 0
unhappyTotal += 1
queueRejectedTotal += 1
```

Отдельный заказ не создаётся.

### 3.3. Истечение терпения

```text
waited = фактические тики в queueWaiting
timeoutSteps = floor(waited / max(1, queuePatience))
penalty = min(5, 1 + timeoutSteps)  // на исходе базового таймера обычно -2

popularity -= penalty
satisfiedStreak = 0
unhappyTotal += 1
queueTimeoutTotal += 1
```

При обычном уходе сразу после истечения таймера штраф равен -2. Более долгое фактическое ожидание, например из-за отложенного тика обработки, увеличивает штраф до -5. Рейтинг ограничивается диапазоном 0–100.

### 3.4. Успешная посадка

Гость покидает очередь без штрафа. Время ожидания сохраняется в статистике `queueSeatedTotal` и `queueWaitTicksTotal` для среднего времени ожидания. Серия недовольных не создаётся.

## 4. Визуал и взаимодействие

- У двери отображаются до 5 силуэтов в порядке FIFO.
- Это визуальные позиции, привязанные к реальным ID гостей, а не дополнительные гости.
- Над первым гостем — компактная шкала терпения.
- При полной очереди силуэт нового гостя не создаётся; показывается короткое уведомление «Очередь заполнена: рейтинг -1».
- Освобождение места запускает посадку первого гостя без клика игрока.
- Визуальные смещения очереди не участвуют в коллизиях мебели и не сохраняются.

## 5. Миграция и сохранения

### 5.1. Предлагаемые поля `GameState`

| Поле | Назначение | Дефолт для старого сейва |
|---|---|---|
| `guestQueue: string[]` | ID гостей в FIFO | `[]` |
| `queueRejectedTotal` | Ушедшие из-за полной очереди | `0` |
| `queueTimeoutTotal` | Ушедшие по таймеру | `0` |
| `queueSeatedTotal` | Успешно посаженные из очереди | `0` |
| `queueWaitTicksTotal` | Суммарное ожидание | `0` |
| `arrivalProgress` | Дробный накопитель спроса | Текущий `spawnProgress`, нормализованный к новой модели |
| `peakStats` | Текущий/последний результат пика | Нейтральный объект, см. спеку пика |
| `dailyQuestState` | Дата и прогресс ежедневного задания | Пустая ротация на текущую дату |
| `hiredCooks` | Будущее LOGIC-7 | Число существующих поваров, обычно 1 |
| `boughtStoves` | Будущее LOGIC-7 | Число существующих плит, обычно 1 |

В объекте гостя:

| Поле | Назначение | Дефолт |
|---|---|---|
| `queueEnteredAt` | Тик постановки | `undefined` |
| `queueWaitedTicks` | Накопленное ожидание | `0` |
| `queuePatience` | Индивидуальный лимит | Вычисляется при постановке |

### 5.2. Правила `normalizeState`

- Неизвестные и повреждённые ID из `guestQueue` удаляются.
- Гость получает не более одного состояния: очередь, посадка, еда или уход.
- Таймеры приводятся к конечным неотрицательным числам.
- Счётчики статистики ограничиваются разумными неотрицательными целыми.
- Старые `purchasedGuestSlots` сохраняются в диапазоне 0–10 и автоматически участвуют в `slotDemand`; поле `legacy` не требуется.
- Старые `guestLimit` и `maxGuestLimit` можно сохранить для совместимости чтения, но новая симуляция не использует их как искусственный предел спроса.
- Один существующий повар и одна плита остаются конфигурацией 1/1. Отсутствие объекта означает 0 для соответствующего звена и не приводит к автоматической бесплатной покупке.
- Прогресс заданий и денежные итоги не пересчитываются задним числом по новой формуле.

### 5.3. Что не сохранять

- Открытые панели, поиск магазина и страницу пагинации.
- Силуэты и экранные координаты очереди.
- Подсветку предупреждения пика и временные уведомления.
- Кэши путей, raycast, Three.js-объекты и производные значения `capacity / arrivalRate / throughput`.

### 5.4. Обязательные будущие проверки миграции

- Сейв без новых полей открывается с пустой очередью и 1/1 кухней.
- Сейв с 10 слотами получает все 10 бонусов спроса.
- Сейв с гостями не дублирует их в очереди.
- Старые деньги, рейтинг, сотрудники, мебель и выполненные задания не изменяются.

## 6. Открытые вопросы

1. **Усреднять ли блюда в `T_cook` или считать по фактическому меню?** Вариант: фиксированные 8 тиков для простого HUD / взвешенное среднее доступных блюд. Не блокирует реализацию очереди; блокирует точную калибровку `throughput`.
2. **Показывать поток за тик или за 60 тиков?** Вариант: только за 60 / переключаемая подробность. Не блокирует симуляцию; для HUD рекомендуется за 60.
3. **Давать ли гостю в очереди желаемое блюдо заранее?** Вариант: выбирать при посадке / при постановке. Не блокирует; рекомендуется при посадке, чтобы не создавать заказы без места.
