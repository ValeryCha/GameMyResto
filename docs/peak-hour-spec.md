# Пиковый час: стресс-тест ресторана

Пик сохраняет текущий цикл, но получает измеримую цель, риск и награду. Документ не описывает реализацию кода.

## 1. Цикл

- Цикл: **180 тиков**.
- Пик: первые **60 тиков** цикла.
- Обычное время: оставшиеся 120 тиков.
- Предупреждение: за **10 тиков** до начала следующего пика, то есть в тиках 170–179 цикла.
- `peakFactor` для `arrivalRate`: **1.50**.

Во время предупреждения HUD показывает «Пик через N» и текущее лимитирующее звено. Это позволяет игроку понять готовность, но не требует дополнительного ручного включения пика.

## 2. Метрики одного пика

В начале пика создаётся новая сессия статистики:

| Метрика | Описание |
|---|---|
| `peakId` | Номер цикла, вычисляется из тика |
| `startedAtTick` | Первый тик пика |
| `arrived` | Все появившиеся попытки прихода |
| `seated` | Гости, получившие место |
| `served` | Полностью обслужённые гости, оплата которых отнесена к этому пику |
| `unhappy` | Все недовольные уходы, связанные с пиком |
| `queueRejected` | Ушедшие из-за полной очереди |
| `queueTimeout` | Ушедшие по терпению очереди |
| `revenue` | Базовая выручка и чаевые за пик |
| `bonusCoins` | Отдельно начисленная награда за результат |

Гость, пришедший до пика, но обслуженный во время пика, учитывается в `served`, но не в `arrived`. Для итоговой оценки используется отдельное число `peakGuests = arrived + carriedIn`, где `carriedIn` — активные гости на старте. Это исключает искусственно завышенную эффективность.

## 3. Эффективность

```text
resolved = served + unhappy
completion = resolved / max(1, peakGuests)
serviceRatio = served / max(1, resolved)
efficiency = round(100 × serviceRatio)
```

До завершения пика прогресс отображается как «Обслужено X · недовольных Y», а не как финальный процент. В итоговой панели основной текст содержит обе метрики: «Обслужено 12 из 15 гостей · завершено 80% · сервис 100%», если оставшиеся 3 гостя ещё не завершили обслуживание и не ушли недовольными. Для награды используется `serviceRatio`; `completion` поясняет незавершённый остаток.

Гости, оставшиеся в ресторане на конец пика, переносятся в следующий цикл и не считаются автоматически недовольными.

## 4. Награды

### 4.1. Чаевые во время пика

- Множитель чаевых: **×1.50** к текущему `tipMultiplier`.
- Применяется только к оплате, завершённой во время пика.
- Не умножает базовую цену блюда и не меняет постоянную экономику вне пика.

### 4.2. Итоговые уровни результата

| Результат | Условие | Награда |
|---|---|---|
| Отличный пик | `efficiency >= 90`, `queueRejected + queueTimeout = 0`, обслужено не менее 5 | `bonusCoins = 100 + 20 × level`, `bonusXP = 50` |
| Хороший пик | `efficiency >= 75`, обслужено не менее 3 | `bonusCoins = 50 + 10 × level`, `bonusXP = 20` |
| Пик пройден | Остальные случаи | Только обычная выручка и чаевые |

Награда выдаётся один раз на `peakId`. Повторная загрузка сейва не создаёт её повторно.

### 4.3. Идеальный пик для заданий

Отдельный флаг `perfect = true` ставится, если:

- `peakGuests >= 5`;
- `unhappy = 0`;
- обслужены все гости, завершившие цикл в этом пике;
- нет отказов полной очереди и таймаутов.

Флаг используется побочными и ежедневными заданиями. Он не добавляет третью денежную награду сверх таблицы.

## 5. Риск и связь с очередью

- Пик повышает только спрос; он не добавляет бесплатные места, блюда или сотрудников.
- Если `arrivalRate > throughput`, растёт очередь.
- Полная очередь и истёкшее терпение применяют штрафы из `guest-system-spec.md`.
- При нулевой вместимости пик не блокируется: он быстро показывает неподготовленность через отказы.
- Отрицательная эффективность не отнимает ранее заработанные монеты и не сбрасывает уровень.

## 6. HUD и уведомления

- За 10 тиков: янтарный значок таймера «Пик через 10…1».
- Во время пика: «Пик · 42 с» и текущие `served/unhappy`.
- После пика на 5–8 секунд: компактная плашка результата, эффективность и награда.
- Последний результат доступен в панели прогресса после исчезновения плашки.
- Существующая полоса уровня не меняется.
- Все интерактивные элементы имеют тач-цель не менее 44×44 и сохраняют доступные имена.

## 7. Сохранение и миграция

Предлагаемая структура:

```text
peakState {
  activePeakId: number | null
  rewardedPeakIds: number[]
  current: PeakStats | null
  last: PeakResult | null
}
```

Правила:

- Старый сейв получает `activePeakId = null`, `rewardedPeakIds = []`, `current = null`, `last = null`.
- При загрузке активный пик восстанавливается по текущему тику; статистика не fabricateируется за прошедшее время.
- Если старый сейв попал в середину пика, начинается нейтральная сессия с текущего тика без ретроактивных наград и штрафов.
- `rewardedPeakIds` можно хранить ограниченным списком последних 30 циклов; повтор старого ID не даёт награду.
- Временная анимация предупреждения и видимость итоговой плашки не сохраняются.

## 8. Будущие сценарии приёмки

- Предупреждение начинается ровно за 10 тиков.
- Пик умножает спрос на 1.5 и длится 60 тиков.
- Чаевые ×1.5 применяются один раз к расчёту.
- Награда за один `peakId` не выдаётся повторно после перезагрузки.
- Очередь увеличивает `unhappy` только по фактическим причинам ухода.
- Идеальный пик доступен при подготовленной конфигурации 5/5 официантов/стоек и достаточной кухне.
- Конфигурация 1/1 кухни при высоком спросе создаёт измеримую очередь без остановки симуляции.

## 9. Открытые вопросы

1. **Учитывать ли гостей, перенесённых с прошлого пика, в знаменателе награды?** Вариант: включать через `carriedIn` / оценивать только новых. Не блокирует цикл; рекомендуется включать для честной оценки.
2. **Показывать итог автоматически или только в прогрессе?** Вариант: короткая плашка + запись в прогрессе / только прогресс. Не блокирует симуляцию; рекомендуется первый вариант.
